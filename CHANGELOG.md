# Changelog

## 1.0.1 — 2026-09-29

Security hardening before a wider release. Nothing new to learn: the skills, commands and results keep their shape.

- **show-local's own requests never reach this computer or the local network on a remote site's word.** The title of a plain remote page, and every redirect a local page's readiness check follows once it has left the local host, are fetched public-only: the address a name resolves to is checked as the connection is made (a `lookup` that refuses any address that is not public, with Node 20's `all: true` form too), and IP literals before connecting. Refused: loopback, `0.0.0.0`, the private networks, link-local (169.254.169.254 included), carrier-grade NAT, multicast and the other reserved ranges, and IPv6 addresses that carry such an IPv4 address (`[::ffff:127.0.0.1]`, which Node writes `[::ffff:7f00:1]`, NAT64, 6to4). Before, a redirect to `[::ffff:127.0.0.1]`, to a name that resolves to 127.0.0.1 (`127.0.0.1.nip.io`), or to a home-network or metadata address was followed. Such a page still opens; its open is reported as "cannot confirm", with the reason.
- **Titles reach Claude short and plain.** Page titles, window titles, process names and server log lines in a result are cut to 120 characters (300 for a log line), with control characters, line breaks and invisible characters (bidirectional overrides, zero-width characters, Unicode tag characters, variation selectors) removed. The window is still matched against the whole title. The three skills now tell Claude that `evidence`, `notes`, `window` and titles are data from the page, never instructions.
- **System programs by full path.** On Windows, PowerShell, `reg`, `netstat` and Explorer now run from the Windows folder by their full path, as `cmd.exe` and `taskkill` already did, so a file of that name in the project folder can never run instead (Windows looks in the working folder first). A relative or network `%SystemRoot%` is ignored. On macOS, `open`, `osascript`, `plutil`, `ps`, `lsof` and `xattr` run from their fixed system paths.
- **Documents that can carry macros are revealed, not opened:** `.doc`, `.xls`, `.ppt` and their templates, macro-enabled Office files (`.docm`, `.xlsm`, `.pptm`, `.xlsb`…), OpenDocument files and `.rtf` (which can embed objects that load as it opens). `.docx`, `.xlsx` and `.pptx` still open.
- **An HTML file must really be HTML:** a link named `page.html` that leads to a script, or a Finder alias named so, is revealed in its folder, as a link or alias named like a document already was. Older Finder aliases (an empty file with the alias bit in its Finder flags) are recognised too.
- **macOS and Linux are beta**, and CI now checks them beyond unit tests: on GitHub's macOS runner with the real `open` and Finder (an HTML page, a PDF, a folder with its main file selected, and a `.command` script, an `.app`, a Finder alias, links and a quarantined script that must be revealed and never run, each next to a control that shows the same kind of file does run when opened directly), and on Ubuntu, what reaches `xdg-open`, `gdbus` and the browser.
- **Repository and CI:** the workflow runs with a read-only token, its actions are pinned to commit SHAs (Dependabot keeps them current) and check out without keeping credentials; CodeQL scans the code; private vulnerability reporting, secret scanning and push protection are on; `main` cannot be force-pushed or deleted, and release tags cannot be moved or deleted.

## 1.0.0 — 2026-09-29

First release.

- `show` skill: opens a result on the user's own computer (default browser, file manager or default app) and verifies that the window came up before reporting it. Every reply gives the full path or URL as a clickable link. "Opened" is said only on real proof (`verified: true`): a window whose title contains the expected page, file or folder name appeared or changed after the open, or the browser's own `GET` reached show-local's server log after the open. Another window that merely changed its title never counts. When there is no way to check (`verified: null`), the reply says it cannot confirm the open, with the reason; when the check fails (`verified: false`), it says it could not verify. Neither ever says "opened", and neither guesses: no "probably", "likely" or odds, in English or in Hebrew.
- `show-serve` skill: runs a static folder or a project's dev server for the session, opens it, and lists and stops the servers show-local started. Static servers take the first free port from 4400 that no other `.claude/launch.json` configuration claims, and a folder keeps its port while its server runs or its `.claude/launch.json` entry exists. It replies in the user's language.
- `show-doctor` skill: read-only diagnosis of the default browser, file associations, window-title access, ports and running servers.
- `scripts/show.mjs`: one dependency-free CLI (Node 18+) behind all three skills. It covers detection, a loopback-only static server with path-traversal, dotfile, symlink and Host-header protection, byte-preserving `.claude/launch.json` merging, and verification adapters for Windows (tested end to end), macOS and Linux (unit-tested).
- `plan` opens nothing. With `--desktop` it adds or updates the project's `.claude/launch.json` entry, which is what that flag is for; the help text and the READMEs say so.
- Headless runs (`claude -p`, a subagent, a workflow step, a script, a CI job, an SDK program): `show.mjs oneshot <target>` is one foreground command that starts the server (the static one in-process, or `dev-run` for a dev project), opens and verifies the page like `next.then`, keeps serving for `--linger` ms (default 3000), stops everything, and prints the open result with `server: { stopped: true, port, lingerMs }`. `stopped` is `false` when the port still answered after the stop, or when a server that was already running was used and left running (`server.note`); the skills then never say that the server was stopped, and name the port instead. `--headless` forces a headless plan, whose `next` is then only `{ oneshot }`; the skills pass it when Claude is a subagent or a workflow step, which inherit the desktop app's `CLAUDE_CODE_ENTRYPOINT`. No background task is left behind, so no task notice follows the final reply.
- Server lifetime: `serve` and `dev-run` check every second that their parent process is still there (`kill(ppid, 0)`), and on Windows also the Claude Code process above the shells the Bash tool puts in between. They exit when either is gone, so a closed or killed session leaves no server behind. A process that has ended but was not yet collected by its parent (a zombie, on macOS and Linux) counts as gone.
- Paths with characters that Claude Code's Bash tool refuses (`;`, `&` and `|`, even inside quotes, and `'\''` as "obfuscation"), or that would end or expand a quoted word (`'`, `"`, `$`, a backtick, a POSIX backslash), travel as percent-encoded `file:///` URLs. Every command that takes a path accepts that form, the printed `next.*` commands use it where needed, and the skills tell Claude to pass such a path that way instead of escaping it.
- `dev-run <root> --port P` runs a project's dev server: it starts `npm`, `pnpm`, `yarn` or `bun run dev` with the project folder as its working folder, so the path never appears on a command line (on Windows `cmd.exe /d /s /c "<runner> run dev"`). It records itself for `servers` and `stop`, watches its parent, and ends the dev tool's whole process tree on SIGINT, SIGTERM, parent death or exit (Windows `taskkill /PID <pid> /T /F`, macOS and Linux a detached process group). A dev plan's `next.start` and the desktop app's launch.json entry (`runtimeExecutable: "node"`) both run it, so a project path with `&` or `%VAR%` in it is no longer mangled by `cmd.exe`.
- The dev port comes from the dev script first, then from the project's own config (`server.port` in a Vite or Astro config, `devServer.port` for Nuxt, `port` in `angular.json`, `PORT=` in `.env`, `.env.local`, `.env.development` and `.env.development.local`), and only then from the framework's default (`vite preview` is 4173, the Vite preview server's own default). The result names the source (`config:<file>` or `env:<file>`). A config that sets the port to something other than a plain number gives `dev-port-unknown`, never the default, and so does a dev script that names several ports, whose result lists them in `candidates`.
- Long Windows paths: an HTML file whose path is longer than 256 characters (too long for `file:///`) is opened through its 8.3 short name (`shortPath: true`, looked up through PowerShell with the path in an environment variable), so its link keeps working after the session; the reply still shows the real full path. Only when there is no short name (8.3 names turned off, or still too long) is it served, and the reason and the reply then say the link works only while the session is open. A PDF, video, image or folder with a path that long is opened through its short name too, and the window check accepts either spelling.
- Linux: pages and HTML files open through the default browser's own `.desktop` `Exec` line (as `xdg-settings` names it), folders through `gdbus` and `org.freedesktop.FileManager1` (which can select the main file), and `xdg-open` is the fallback for both and the route for app files. So `.html` associations do not decide the browser on Linux either. A session with `WAYLAND_DISPLAY` set counts as Wayland even when XWayland also sets `DISPLAY`, so a missed native window gives "cannot verify", not "did not open".
- macOS: a folder whose name has a dot (which Finder would open as a package) is revealed in its parent, and the check now waits for the parent's Finder window. Windows: the doctor names a browser or app whose path has non-ASCII characters correctly, and treats `.html` and https as the same browser whenever they share a ProgId.
- `SHOW_LOCAL_TIMEOUT_MS` sets how long the window check waits (default 5000 ms), for slow machines. A value above the default also extends a direct open's time budget by the same amount, so the whole wait is used. With `0` no window is looked for, so the open is `verified: null` (never `false`) unless show-local's server log proves it.
- Results name the browser that was used (`browser`), and every failed result carries `verified: false` with its detail as the evidence. A direct open (a URL, a file, a folder or an app) finishes within 9.6 s end to end (plus whatever `SHOW_LOCAL_TIMEOUT_MS` sets above its default), including the window watcher's start-up: the window check gets whatever the budget has left, at least 1 s.
- A local server counts as ready only on a final `200` (a remote page on any `2xx`), after following up to 5 redirects. The check asks with a browser's `Accept` header (`text/html`), so a single-page app's history fallback serves its deep links to it as it does to the browser. A local page that redirects to a remote address that could be a one-time link (a hosted sign-in such as OAuth, Clerk or Auth0) is opened without fetching that address, with `verified: null`. The server-log proof counts only `200`, `206` or `304` lines for the final path, never show-local's own requests or Claude's preview pane (`Electron/`).
- A folder open that asked to select a file reports `selected: true`, `false` or `null` (could not be checked). A folder window that was seen stays `verified: true`, but with `selected: false` the evidence and the reply say the file was not selected.
- An HTML page also gets a server when the local scripts it loads (not only the page itself) use ES modules, `fetch` or JSON, or when it loads a local data file next to it (`json`, `csv`, `tsv`, `xml`, `geojson`, `topojson`, `txt`, `wasm`, `glb`, `gltf`), also through `d3.json`, `$.getJSON`, `axios.get` and the like.
- More media types open in their app: video (`avi`, `mkv`, `webm`, `wmv`, `mpg`, `mpeg`, `flv`, `3gp`, `mts`, `m2ts`, `m4v`, `ogv`, `mxf`, `vob`, `f4v`, `dv`, `divx`, `asf`, `m2v`), images (`jfif`, `avif`, `heic`, `heif`, `tif`, `tiff`), camera RAW (`dng`, `cr2`, `cr3`, `nef`, `arw`, `orf`, `rw2`, `raf`), audio (`wma`, `aiff`, `aif`, `opus`, `mka`) and `xps` documents. `.ts` and `.mod` stay off the list: they are also TypeScript and Go module files. A type that is still not on the list is shown in its folder, and the reason says it is not on show-local's list, never that it is not a video or an image.
- `servers` and `stop <port>` also cover the dev servers show-local started or opened a page on. The skills tell Claude to stop the servers it started when the user is done. A `dev-run` or `oneshot` entry is listed while its show-local process and that process's guard both run, and stopped only while the OS confirms they are still exactly those; an entry left behind whose pids other processes now have is removed (`removed` in the `stop` result), never stopped. On Windows, `stop` never ends a `oneshot` process's whole tree, because the browser it opened the page with can run under it.
- A dev-server page is proved by the HTTP answer and the window title only: a dev server keeps whatever it logs in its own output, which show-local cannot read. The browser's own `GET` in the server log is a second proof for show-local's static server only. A dev server binds wherever the project configures it; show-local does not force `127.0.0.1` on it.
- Never runs what it shows: only known viewable types (documents, images, video, audio, text) open in their app; programs, scripts, shortcuts, files of unknown type or with no extension, and `.app` bundles are revealed in their folder.
- Privacy: a remote address that could be a one-time link (a query string, a fragment, or a long or token-like path segment) is never fetched before opening, so its open is reported as "cannot confirm". A plain remote address is requested once, by show-local and without the browser's cookies, only to read its title for the window check. `port-busy` reports only the pid and process name of the process holding the port.
- `install.sh` and `install.ps1` stop with an error and a non-zero exit code when a step fails.
- Docs: the READMEs describe the optional bare `/show-local` personal command (a plugin can only provide `/show-local:show`), with its exact file content and how to remove it, and the uninstall steps now also delete the state folder (`%TEMP%\show-local` on Windows, `$TMPDIR/show-local-<uid>` on macOS, `$XDG_RUNTIME_DIR/show-local-<uid>` or the temp folder on Linux, and `~/.cache/show-local`). The Hebrew README addresses the reader in the plural throughout.
- Robustness: Windows 8.3 short names cannot reach dotfiles; symlinks to dotfiles inside the folder are refused; nested pages are served from their site root with per-segment URLs; https dev servers (`--https`) and self-signed loopback certificates are handled; Windows 11 Explorer tabs are told apart; a live but silent server is listed with `responding: false` and stopped only when its pid provably owns the port.
